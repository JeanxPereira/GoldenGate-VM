# Family C: objects, resources and guest memory

Apple side: GPUTask `PGResourceManager::createObject<PGResource*>` @0x1000427EC dispatches on the
`APVObjectEntry` type byte (12-byte entries, `PGObjectListManager::setObjectList` @0x222F40D4C
divides the list length by 0xC; placement entries are 16 bytes). Any other tag ends in
`"Unexpected object type ({}) for resource"`. Tag 7 (serializer object) goes to the typed
`createObject<T>` instantiations instead. Orchard side: `runtime/decode/resource/mod.rs`
(`decode_descriptor` :5558), `runtime/objects/mod.rs`, `runtime/draw/{mod,vulkan,texture_view,render_target}.rs`,
`runtime/mapper/mod.rs`, `runtime/mapping_write/`, `runtime/guest_ram_map.rs`, `qemu/host_ops.rs`.
All Orchard paths are relative to `reims-vgpu/crates/reims-vgpu/src/` on `gg-macos27` (HEAD `ea4dfb5`).
Log counts come from `/tmp/reims-vgpu-fail.5b042af.log` (driven boot, latest complete run).
`175aa0e` and `dznkisak` counts are given where they differ.

## The measured declines, against Apple

1. **`heap_query_no_metal_device` (83).** Each line is `heap_texture_query type=2 fmt=… usage=0x3|0x5 options=0x20` (private 2D textures). On Apple, `heapTextureSizeAndAlign` @0x10004F6E4 asks Metal and always writes the 16-byte reply. On Linux Orchard compiles the stub at `backend/heap_placement.rs:102`, which returns `NoMetalDevice`. `reply_heap_texture_size_and_align` (drain/mod.rs:3684) then returns early and writes no reply. The guest reads whatever is in its reply buffer (zero, or stale). The guest never creates a heap in these runs, which fits a guest that gave up on heap sub-allocation after reading size 0. Fix: compute size and align on Linux, either from `vkGetDeviceImageMemoryRequirements` or from a deterministic formula (sum of the level slices, rows aligned to 256 B, rounded up to 16 KiB, align 16 KiB). Orchard places heap textures as independent host images anyway, so any answer at least as large as the real bytes is safe.
2. **`GuestRefRefused` (39).** All 39 are `OFF compute_dst_mapper_ref_texture … held=R16G16B16A16_SFLOAT|R8G8B8A8 reason=GuestRefRefused{NoBackendImport}` (compute_exec/vulkan.rs:270, from `licence_mapper_ref_texture_surface` mapping_write/vulkan.rs:566/627). On Apple a type-0xB texture is an IOSurface built over guest pages, so a compute write lands in guest memory at no cost. Orchard can only do that through a `VK_EXT_external_memory_host` import of guest RAM, and this backend publishes none (`guest_ram_map.rs:64`). The dispatch then writes a host resident (`compute_dst_host_mapper_ref_texture_unlicensed`), and the copying writeback lands it later. This is expected on hosts without import, not a loss. Cost: one readback copy per dispatch, and correctness hangs on the debt/settle machinery.
3. **`qemu_map_pages_alias_failed` (25).** Apple's `PGMemoryMap newRangeMapping` remaps any page list into one contiguous VA. Orchard's Linux shim can alias only shared file-backed RAM (reims-vgpu-mmio.c:444-451 states this). Anonymous guest RAM refuses at the alias stage with errno 0. Each event is followed by `contig_view_refused … runs=1013` and `mapping_write_runs` (≈1.5–2.3 ms for a 1920×1080 RGBA16F frame). Performance only; frames still land.
4. **`draw_prepare_texture_resolve_missing` types 8/2 (18 draws, plus 18 `draws_skipped_after_engine_refusal` that also drop the pass clear).**
   - 5 × type 8 `view_resolve res_texture_view_opcode`: the bound texture is a view (desc 56 B) whose parent is an **opcode-9 buffer texture** (decline bytes `09000000 40000000 …`; e.g. R8Unorm 104×104, bpr 256). Apple's view constructor accepts any parent that answers `getTexture`, buffer-backed ones included. Orchard's chain collapse (`resolve_texture_view_reasoned` texture_view.rs:345-373) treats every type-8 parent as another view hop and decodes it with `decode_texture_view_descriptor`, which accepts only 7/8/0x1B.
   - 9 × type 8 `buftex_load`: buffer textures in **RGB10A2Unorm (0x5A)**, 106×106 and 28×28. `load_buffer_texture_rgba` (draw/mod.rs:1548) → `RowToRgba8::for_format` has no arm, so the log shows `buftex convert_unsupported`.
   - 4 × type 2 `linear_sample fmt=0x19`: **R16Float** 16×16 / 96×32 normal textures. The same table has no arm. `memo_wrong_type want=[8] memo_ot=2` lines precede them and are diagnostic only.
   On Apple all three are ordinary Metal sampling.
5. **`compute_view_format ot=11 base_fmt=0x21e` (8 binds).** A compute kernel samples a 512×512 mapper-ref IOSurface in format 542. Apple samples the two-plane surface natively, with no validation (`validateIOSurfaceDescriptor` returns true for planar surfaces). Orchard has no table row for 542 (`term=base_undeclared_here`), and `decode_iosurface_texture_descriptor` drops the plane index the 0xC/0x2F/0x39 commands carry.
6. **`resident_chain_abandoned_cpu_recovery` (27; 39 and 92 in the other runs).** `cause=no_metal mid=2/3/30 1920x1080 fmt=0x73`. In this run they are downstream of `draw_prepare_texture_access_unsupported stage=fragment index=3 access=storage`: a fragment shader binds a read_write (storage) texture, which Apple executes natively. Orchard refuses the draw (`draw_vk_nothing_stored`), abandons the chain and lands the previous resident readback through `write_rgba8_image_changed` (draw/mod.rs:2249). Not a Family-C object bug. The repair belongs to the draw/binding family (fragment storage images). Worth checking that the RGBA8 recovery write is widened for a 0x73 mapping (open question 3).
7. **`read_target_texel_not_four_bytes` (27).** `render_flush_lease_declined format=R16G16B16A16_SFLOAT` (engine/mod.rs:3557, render_writeback/vulkan.rs:102). The leased zero-copy readback lends only 4-byte colour. The code treats the decline as a routing answer, and the copying rail follows (`mapping_write_runs bytes=16588800` = 1920·1080·8, native RGBA16F). Apple has no readback here at all: the target's storage is the guest's. Benign. It goes away with VK host import, or with a lease that can lend 8-byte texels.

## Ranked fix list

1. **Heap size/align reply on Linux.** `backend/heap_placement.rs:102` non-macOS arm: compute `SizeAndAlign` from the descriptor via the Vulkan engine's image requirements, or with a conservative formula. About 40–60 lines plus tests. Low risk. Unblocks 83 queries and probably the guest's heap path, which the next items then have to handle.
2. **Sample rail formats.** Add `R16Float` (0x19), `RGB10A2Unorm` (0x5A) (and `R16Unorm`, `RG11B10Float` while there) to `RowToRgba8` and the texel rail (pixel_format.rs:3433-3500, kept in lock-step by its own test). About 40 lines. Low risk. Fixes 13 of the 18 type-2/8 misses.
3. **Views over non-view type-8 parents.** In `resolve_texture_view_reasoned` (texture_view.rs:359-373), stop the chain when the parent's opcode (`texture_view_opcode`) is not 7/8/0x1B. Return it as the base, and let `resolve_sampled_source` route an opcode-9/0x37 base through `load_buffer_texture_rgba` (and 1/52 to the transient resident) with the view's format override and swizzle. About 60–100 lines. Medium risk: chain-cap and memo invariants. Fixes 5 draws.
4. **542 two-plane mapper-ref sampling.** Declare 542 (and its 2P siblings) in `protocol::pixel_format`, carry the plane index out of `decode_iosurface_texture_descriptor`, and add a CPU two-plane gather like `xr10_planes` (plane 0 at offset 0, plane 1 at the mapper's plane offset), producing RGBA8/RGBA16F for compute staging. About 150–250 lines. Medium-high risk: the channel semantics of 542 are inferred, see open question 1. Unblocks 8 compute dispatches.
5. **ICB object tag.** Accept tag 0x14 (and keep 7) in `load_icb_descriptor` (icb/mod.rs:1205) and in `RESOURCE_CONSTRUCTOR_TYPE_MASK` (set bit 19). About 10 lines. Low risk. Prevents a silent refusal the first time the guest makes an ICB.
6. **Heap objects (0xD/0xE) and placed textures.** Decode heap descriptors, give each heap one host allocation, and alias placed textures and buffers at `offset` (Apple: `newTextureWithDescriptor:offset:` / `newBufferWithLength:options:offset:`). About 300+ lines. High risk. Needed only once item 1 makes the guest use heaps.
7. **Dual-plane depth-stencil 260/261** on type 0xC: a depth+stencil rail mirroring `PGDualPlaneBlitTextureResource` (plane 0 depth, plane 1 stencil). About 150 lines. Medium risk. P1, not yet seen.
8. **Mapper-ref buffer 0xF** (buffer view of a mapping), about 50 lines, low risk. **Placement list** parse, about 80 lines, low risk until something consumes GPU VAs.
9. **Map alias / guest import** (items 2, 3 and 7 of the decline list): back guest RAM with `memory-backend-memfd,share=on` on hosts whose GPU accepts it, or a hugepage file. That is configuration, not code, and it carries the documented amdgpu userptr conflict.

## Open questions

1. What exactly is format 542? Its name, and which channels plane 0 and plane 1 hold. Get it from Metal's `MTLPixelFormatGetInfo` table in the guest's Metal framework, or from the guest's `IOSurfaceDevicePlaneDescriptor2` for these mappings (`mapping_gpa_span mid=41..56 pages=48`).
2. What does the guest do with an unanswered heap query? Does it read zero and skip heaps, or does it keep a stale value? Check the reply GVA contents after one query, and confirm that the guest-side caller (guest RE) falls back.
3. Does `mapping_write::write_rgba8_image_changed` widen RGBA8 to RGBA16F for a `fmt=0x73` mapping during `resident_chain_abandoned_cpu_recovery`, or does it write 4-byte texels into an 8-byte surface?
4. `qword_10008AF50` (per-plane blit options for `PGDualPlaneBlitTextureResource`) is inferred as depth/stencil-from-DS. Confirm in IDA.
5. Which object tag does the 26A428 guest serializer assign to ICBs? Apple's host demands 20.
